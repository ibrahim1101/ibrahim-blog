# Deployment

Create the intended GitHub repository and protect its production branch before adding content. Do not upload the original ZIP wholesale without inspecting it: local drafts, evidence, history, backups and secrets must remain private. `.gitignore` excludes those directories for new files, but already tracked files remain tracked until explicitly removed from the Git index.

For Cloudflare Pages connect the repository, select the protected production branch, set root directory `website`, build command `npm run build`, and output directory `dist`. Use Node 24 or later. Only connect the new project; leave existing sites and unrelated DNS records unchanged. Add the new custom domain `blog.ibrahimshaik.com` using the Pages custom-domain workflow. Verify TLS, DNS and that only the protected branch deploys to production. Disable public PR preview deployments or protect them if drafts are sensitive.

## Contact form

The form intentionally displays the public email fallback until configured. To enable delivery, create a Cloudflare Turnstile widget for the intended host and supply `PUBLIC_TURNSTILE_SITE_KEY` at Pages build time and `TURNSTILE_SECRET` at runtime. Configure `CONTACT_WEBHOOK_URL` and `CONTACT_WEBHOOK_TOKEN` as runtime secrets. The HTTPS webhook must be a service you control that accepts a JSON POST `{name,email,message}` with `Authorization: Bearer <token>` and returns a 2xx response only once the message is accepted for delivery. An optional implementation is included in `contact-worker/`; it must be deployed and configured. A webhook response alone is not proof that email arrived. Set up and verify a real delivery service before advertising the form as operational. The Pages function validates input, origin and Turnstile. The supplied delivery Worker additionally requires a per-client Cloudflare rate-limit binding; set its namespace ID to one unique within your account. Cloudflare describes the limit as per-location and it may be exceeded, so it is not a strict global limit. Keep secrets out of Git and test real delivery from the deployed domain.

Pages Functions are in `website/functions/`; ensure your Pages deployment includes them. Confirm the static build, DNS, headers, contact delivery, and branch permissions after deployment. Nothing in this package has created Cloudflare resources or published a real article.

## Included Cloudflare email delivery worker

The optional `contact-worker/` adapter accepts authenticated requests from the Pages function and forwards messages through a Cloudflare Email Service binding. It is not deployed or configured by this repository. Before deploying, enable Cloudflare Email Service on an authorized sender domain and verify the recipient address. Restrict the `EMAIL` binding to the intended sender and destination in `contact-worker/wrangler.jsonc` using your actual addresses; never place tokens in that file. Set Worker secrets `CONTACT_TOKEN`, `CONTACT_FROM`, and `CONTACT_TO`; use a long random `CONTACT_TOKEN`. Deploy the Worker with your own Cloudflare account, and configure Pages `CONTACT_WEBHOOK_URL` to its HTTPS URL and `CONTACT_WEBHOOK_TOKEN` to the same secret. Configure the Turnstile keys separately as described above. Test with a message you are authorized to send and verify the actual inbox before advertising the form. Email Service availability, pricing, sending limits, sender domain verification, and account restrictions must be checked in your account.

The delivery worker hashes the client IP with its secret token for the rate-limit key. Configure the `CONTACT_LIMITER` binding shown in the Worker configuration; delivery fails closed if the binding is missing. Consider additional Cloudflare WAF rules for broader abuse control.
